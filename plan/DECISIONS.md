# Architecture, interface, and decision register

The normative TypeScript types are `src/contracts.ts`; method signatures are `src/index.ts`. This register is the behavioral half of that public contract. No implementation may widen permissions, return credentials, or silently change these shapes.

## Architecture decisions

- **D-001 — Backend plus plugin.** Deliver a hosted GitHub App/OAuth/MCP service and a thin Kimi Code plugin. A manifest-only plugin is rejected because it cannot safely hold the GitHub client secret, private key, webhook secret, or per-user credentials.
- **D-002 — Supported surfaces.** Target Kimi Code CLI and `kimi web` 2.3.3. Do not claim hosted kimi.com connector certification.
- **D-003 — Per-user authorization.** All user-driven GitHub calls use that user's GitHub App user access token. Installation tokens may never authorize a user request. The accessible set is user∩app installation.
- **D-004 — Nested OAuth with consent.** Kimi authenticates to the connector using authorization code + PKCE S256; the connector then proxies GitHub OAuth. Before the GitHub redirect, a connector consent page identifies the MCP client, `github.read` access, canonical resource, and exact downstream redirect URI. Bind consent to the original authorization request and a Secure, HttpOnly, SameSite=Lax browser-transaction cookie, and require a same-origin CSRF token on approval. Consent is single-use and expires in 10 minutes; upstream state is created only after approval. Missing, mismatched, cross-session, replayed, or cross-origin consent submissions fail closed.
- **D-005 — CIMD and DCR.** Support Client ID Metadata Documents and Dynamic Client Registration through one validator. CIMD requires HTTPS and safe bounded fetch. Allow loopback redirect URIs only for loopback client metadata; otherwise require HTTPS. Match redirect URIs by exact string. Reject fragments, wildcard hosts, `client_credentials`, and confidential-client requests. Bound storage abuse with per-IP limits of 10 registrations/minute and 30 OAuth starts/minute, global caps of 10,000 client rows and 5,000 in-flight OAuth transients, and 429 fail-closed admission at a cap. Delete client rows inactive for 30 days only when they have no active grant; transient expiry remains within 15 minutes.
- **D-006 — Connector credentials.** Use opaque random connector access/refresh tokens, never GitHub tokens. Access tokens last 3,600 seconds; refresh tokens last 30 days and rotate atomically. Store only SHA-256 token hashes, bind each grant to subject, client, and canonical resource, and reject replay. Serialize same-grant refresh so concurrent callers receive the same committed generation.
- **D-007 — GitHub credential lifecycle.** Request `offline_access`; require `expires_in` and a refresh token. Encrypt GitHub access/refresh tokens at rest with AES-256-GCM using a 32-byte external key and unique nonce. Serialize refresh per GitHub user and compare-and-swap the credential generation. Revocation deletes credentials and connector grants.
- **D-008 — Least-privilege GitHub App.** Request repository Contents: Read and account Metadata: Read only. Subscribe only to `github_app_authorization`, `installation`, `installation_repositories`, and `installation_suspend` events needed for lifecycle handling. The App is publicly installable on personal accounts/organizations with all or selected repositories.
- **D-009 — Live GitHub reads.** Fix the base URL to `https://api.github.com`, send `X-GitHub-Api-Version: 2026-03-10`, and use `/user/installations`, installation repository pages, Git Trees, and Contents/raw reads. Return 404 for inaccessible repositories to reduce enumeration. Never use cached catalog membership as authorization.
- **D-010 — Bounds and continuation.** Caps are 100 repositories/page, 5,000 tree entries/page, 256 KiB returned UTF-8 content, and 2,000 lines. Tree cursors paginate only connector presentation; propagate GitHub's independent `truncated` flag. File continuations carry byte/line offsets. Invalid UTF-8, symlinks, submodules, and paths containing `..`, NUL, or a leading slash return explicit errors.
- **D-011 — MCP tools.** Expose exactly `github_list_repositories`, `github_get_tree`, and `github_read_file`. Inputs correspond to `PageRequest`/`RepositoryRef`/`FileReadRequest`; outputs correspond to `Page<Repository>`, `TreeResult`, and `FileReadResult`. Return structured JSON plus concise text; `isError=true` for tool failures. No write tools exist.
- **D-012 — MCP HTTP surface.** `POST /mcp` is the only MCP message endpoint. Negotiate 2026-07-28 and required legacy compatibility. Use JSON or request-scoped SSE. Require bearer authentication, audience validation, origin checks where applicable, bounded bodies, and per-request isolation. `GET`/`DELETE` return 405 with `Allow: POST` unless the negotiated SDK transport explicitly requires otherwise.
- **D-013 — PostgreSQL records.** Store OAuth clients, transient consent/state/code grants, connector token hashes/generations, encrypted GitHub credential generations, webhook delivery IDs, and security/audit metadata. Use UUID keys and UTC timestamps. No repository paths, file contents, or source index are persisted. Webhook delivery IDs are unique for idempotency.
- **D-014 — Webhooks.** Verify `X-Hub-Signature-256` over the exact raw UTF-8 bytes with HMAC-SHA256 and constant-time comparison before JSON parsing. Return 401 on failure. Deduplicate delivery IDs. On user revocation, delete both credential domains; on installation changes, invalidate only advisory catalog cache.
- **D-015 — Cache policy.** Cache only metadata for at most 60 seconds and per GitHub user. Do not cache source content. Every live API 401/403/404 invalidates relevant metadata. Permission checks still go through GitHub user-token APIs.
- **D-016 — GitHub failures.** Use a 10-second upstream deadline, at most two retries for idempotent reads, deterministic jitter in tests, and `Retry-After`/`x-ratelimit-*` handling. Never hide persistent 403/429 behind stale authorization data. If a GitHub user-token call still returns 401 after its single-flight refresh attempt, delete that user's GitHub credentials and connector grants before returning `REAUTHENTICATION_REQUIRED`; do not apply that rule to authorization-related 403/404 responses. Return `GITHUB_RATE_LIMITED`, `GITHUB_UNAVAILABLE`, or `REAUTHENTICATION_REQUIRED` as appropriate.
- **D-017 — Logging and retention.** Structured logs contain request ID, subject pseudonym, route, status, duration, and error code; never tokens, authorization headers, client secrets, private keys, repository content, or full repository paths. OAuth transient rows expire within 15 minutes; security/audit metadata is deleted after 30 days. Sweeps are idempotent.
- **D-018 — Configuration.** Required: canonical public origin/resource, database URL, GitHub client ID/secret, webhook secret, 32-byte token-encryption key, trusted proxy setting, and alert target. The GitHub App private key is optional in the MVP because user tokens replace installation-token reads; if absent, no code path may attempt App-JWT installation authentication. Startup fails closed and redacts values.
- **D-019 — Deployment.** Provide non-root Docker image, Compose with internal PostgreSQL, Caddy TLS, healthchecks, resource limits, persistent database volume, migrations, and rollback-compatible releases. Use only official `node:24.22.1-trixie-slim`, `caddy:2.11.7-alpine`, and `postgres:18.6-trixie` images; S-000 resolves and records each linux/amd64 manifest digest, and all Docker/Compose/release files use those immutable digests rather than mutable tags. If an exact tag or digest cannot be resolved, S-000 blocks rather than substituting an image. Production hostname, DNS, host credentials, alert destination, and public release require G-002.
- **D-020 — Frozen verification.** The 30 tests T-001…T-030 are normative. Implementation replaces stubs without changing tests. New defects require the formal unfreeze/red/re-freeze amendment path. The test harness supplies only deterministic non-secret fixture defaults explicitly described in S-001; production configuration never inherits test defaults. Verification adapters execute the named probes and external checks rather than returning hard-coded success objects.
- **D-021 — Performance.** Use mocked GitHub, 50 concurrent MCP requests, five runs, p95 connector-added latency <300 ms, errors <1%, service memory <512 MiB, and run-to-run p95 variance ≤20%. Each run executes one excluded warm-up wave followed by 15 measured waves; every wave contains 50 simultaneous requests: one GitHub-maximum recursive tree fixture (7 MiB JSON/100,000 entries), 24 maximum 256 KiB/2,000-line file reads, and 25 100-repository pages. Record aggregate and per-tool p95/error values for every wave; every tool's measured p95 must be <300 ms, and no maximum-payload sample may be discarded. Exclude GitHub time by harness instrumentation, not by discarding slow samples.
- **D-022 — Mutation.** Stryker 10.1.1 with Vitest runner covers implemented `src/**/*.ts` except type-only contracts. Score must be ≥85%; every survivor gets a test through the amendment process or a mutant-class justification in `reviews/MUTATION.md`.
- **D-023 — Plugin package.** `kimi.plugin.json` declares only `mcpServers.github.url = https://<gate-hostname>/mcp`; no token, command, secret, or environment credential. Installation and login documentation uses the plugin repository and `/mcp-config login github`. Version 0.1.0, SemVer, Apache-2.0.
- **D-024 — Release evidence.** Release requires all frozen tests, reviews, mutation, secret/dependency scans, staging rollback/alert tests, and live Kimi CLI/web OAuth plus read-only tool calls. Publish only after G-002.
- **D-025 — Fresh reviews.** S-REVIEW, S-ADVERSARIAL, and S-RETRO require fresh-context agents. If unavailable during implementation, record the limitation and keep G-002 unsatisfied; do not label a same-context review independent.

## Public HTTP and error contract

| Route | Success | Failure behavior |
|---|---|---|
| `GET /.well-known/oauth-protected-resource/mcp` | RFC 9728 metadata for canonical `/mcp` resource | 404 only if route is genuinely unsupported; never redirect to attacker URL |
| `GET /.well-known/oauth-authorization-server` | Issuer, authorization/token/registration endpoints, PKCE and grant metadata | 500 `server_error` without internals |
| `POST /oauth/register` | DCR public client metadata | 400 `invalid_client_metadata` |
| `GET /oauth/authorize` | Consent page, never immediate GitHub redirect | 400 for invalid client/redirect/resource/PKCE |
| `POST /oauth/consent` | Single-use GitHub authorization redirect | 403 for consent/session mismatch |
| `GET /oauth/github/callback` | One connector code redirect to exact client URI | 400 `invalid_state`; deny on GitHub error |
| `POST /oauth/token` | `TokenGrant`; form encoding; no GitHub credential | 400 `invalid_grant`/`invalid_client`/`unsupported_grant_type` |
| `POST /oauth/revoke` | 200 after idempotent grant revocation | 401 for invalid client binding |
| `POST /mcp` | MCP JSON/SSE result | 401 + `WWW-Authenticate` for missing/invalid token; 403 for insufficient scope; JSON-RPC tool errors otherwise |
| `POST /webhooks/github` | 202 after authenticated idempotent handling | 401 invalid signature; 409 malformed duplicate conflict; 422 validly signed unsupported payload |
| `GET /health/live` | 200 process health | 503 only when event loop/process cannot serve |
| `GET /health/ready` | 200 database/token-key ready | 503 with check names, no secrets |

Application errors carry `code`, safe `message`, HTTP `status`, and optional `retryable`; tool errors use the same code in structured content. Required codes include `INVALID_CONFIGURATION`, `INVALID_CLIENT_METADATA`, `UNSAFE_METADATA_URL`, `INVALID_REDIRECT_URI`, `INVALID_RESOURCE`, `INVALID_STATE`, `INVALID_GRANT`, `INVALID_TOKEN`, `UNSUPPORTED_GRANT_TYPE`, `REAUTHENTICATION_REQUIRED`, `NOT_FOUND`, `INVALID_PATH`, `NOT_UTF8_TEXT`, `UNSUPPORTED_ENTRY`, `GITHUB_RATE_LIMITED`, `GITHUB_UNAVAILABLE`, and `INVALID_SIGNATURE`.

## Pre-decided fork rules

- **D-026 — Unexpected API shape:** if GitHub, MCP, or Kimi returns an unexpected but parseable shape, reject it at the boundary, capture a redacted fixture, and add a contract test through amendment; do not guess fields or weaken validation.
- **D-027 — Dependency install fails:** if the exact lockfile install fails, retry once on local storage; then inspect registry/integrity evidence. If a version is yanked or incompatible, halt with `BLOCKED.md`; never float to an unpinned version.
- **D-028 — Performance miss:** if T-025 fails, preserve all five outputs, profile connector-added time/memory, optimize without weakening bounds or authorization, and rerun. If two fix attempts still miss, stop before G-002 with measurements and a rescope proposal.
- **D-029 — Vulnerability:** if a Critical production vulnerability appears, block release immediately. If a High appears, block unless a fixed lockfile passes all tests; no runtime waiver is allowed without G-002 rescope. Weekly alerts become an operations ticket within one business day.
- **D-030 — Staging failure:** if staging startup, migration, health, OAuth, or smoke fails, keep production untouched, restore the previous known-good staging image, and fix from logs. After three failed attempts, halt with `BLOCKED.md`.
- **D-031 — Post-release health failure:** if readiness fails for two consecutive 30-second probes or connector error rate exceeds 1% for five minutes, execute `plan/OPERATIONS.md` rollback immediately and halt further rollout.
- **D-032 — Monitoring alert during rollout:** if a synthetic or real alert does not reach on-call, deployment is not complete. Pause rollout, repair alerting, rerun T-028; never disable the alert to pass.
- **D-033 — Default:** choose the most reversible option that does not expand scope, log it in `DEVIATIONS.md`, and continue — unless it touches frozen tests, security, data integrity, a public interface, research integrity, or evidence class, in which case halt and write `BLOCKED.md`.
